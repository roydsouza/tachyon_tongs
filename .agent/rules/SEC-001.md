# SEC-001: Ironclad Verification & Environment Identity

## The Principle
Security-critical operations (Genesis ceremonies, key recovery, signing delegations) MUST NOT rely solely on in-process unit tests or mocked functional tests. Furthermore, the testing environment MUST BE IDENTICAL to the user's runtime environment.

## The Debacle: The "Environmental Disconnect"
Phase 25.2 failed because the Agent ran tests in a project-local `venv` while the User ran the command via a global `pyenv` shim. This created a "False Positive" where the Agent saw dependencies the User did not.

## Mandatory Implementation
1. **Zero-Mock E2E**: Any function exposed as a `tt` security ritual must have a corresponding "Ironclad" test using `subprocess.Popen` to interact with the REAL binary.
2. **Environment Identity**: Before running security tests, the Agent MUST identify the user's active Python path (e.g., `which python3`) and ensure the test runner uses THAT SPECIFIC BINARY. Testing in a `venv` when the user is not in a `venv` is a violation of this rule.
2. **Environment Parity**: Tests must verify real OS-level interactions (Keychain, filesystem persistence, standard error streams).
3. **Traceback Zero-Tolerance**: Any occurrence of `Traceback`, `NameError`, or `AttributeError` in the stderr of a security command is a CRITICAL FAILURE, even if the exit code is 0 (caught by a top-level broad except).
